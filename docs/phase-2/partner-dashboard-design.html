Partner Dashboard Design

A separate, white-labelled dashboard where principals and management of partner school groups (first: VIBGYOR) view and download their schools' academic data, which lives in CADB. Projects (School Integrated Program and After School Program) become a first-class concept that scopes all of it.

Status Draft v0.1 Date 11 Oct 2026 Baseline production v1.24.0 Branch phase-2

Summary

CADB already holds the data VIBGYOR management wants: students, batches, exams, marks, attendance and assignments. Phase 2 adds three things on top, without changing the live CADB app:

  1. Projects. Each partner runs one or more projects (SIP or ASP). A project has a start date, a starting academic year, grades, schools, and a board for each school's grade range. Batches are assigned to a project.
  2. Partner access. Partner users (principals, regional heads, management) get grants by project, by school and by report. A new user sees nothing until an administrator grants access.
  3. Partner dashboard. A view-only web app on a neutral domain, carrying no Centum branding, where partner users browse metrics and download PDF and Excel reports, down to individual student level where granted.

Everything is view-only for partners. The only writes are internal: project setup, access grants, and a log of every view and download.

Guardrails

1. Nothing goes live on cadb.centumacademy.com

The CADB web app and API on production stay at v1.24.x for the whole of Phase 2 development. Phase 2 runs as separate services. The only production change at go-live is an additive database schema (new tables in their own namespace) plus the new services. See Architecture.

2. Staging is a replica of production

Staging runs the same release tag as production, and its database has the same migrations applied. After every production release, the same tag is deployed to staging the same day. Phase 2 services run beside it on staging. See Environments.

3. Isolated, versioned, reversible

All Phase 2 work happens on the phase-2 branch, with tagged builds. Every database change only adds things and has a written reverse script. Any deployment can be rolled back by redeploying the previous tag. CADB itself never needs rolling back, because it is never changed.

4. No trace of Centum in anything a partner sees

Domain, emails, page titles, code bundles, file metadata and data fields are all neutral. An automated build check fails on any occurrence of "centum". See Confidentiality.

Architecture

Two shapes were considered. Option B is recommended because it is the only one that keeps guardrail 1 with no CADB release at all.

A. Inside CADB

  • Partner API routes and the Projects / Partner Access screens added to the CADB API and portal.
  • Admins manage everything in the CADB portal they already use.
  • Needs a CADB production release at go-live and for every later partner change. This breaks guardrail 1.

B. Separate partner services recommended

  • New apps/partner-api, apps/partner-web (dashboard) and apps/partner-admin (internal console) in the same repo.
  • Read CADB tables through a read-only database login. Their own tables live in a separate partner schema that CADB's migrations never see.
  • CADB app untouched. Partner services can be released and rolled back on their own schedule.
  • Cost: your team uses a separate internal console to manage projects and access, rather than a tab in CADB.

Rules the architecture enforces

  • The browser never talks to partner-api or CADB. Only the partner-web server does, so no internal address, header or error message reaches a partner.
  • The database refuses writes from the partner services to any CADB table. A bug cannot change student, fee or HR data.
  • Separate identities. Partner users are stored in partner.PartnerUser, not as Employees or Students. Their credentials do not work on the CADB portal, and CADB tokens do not work on the partner API.
  • Production load. Heavy totals are cached for 15–30 minutes, so dashboard traffic stays light on the live database.
  • Admin logins. partner-admin is for Centum staff only. Its login is separate from partner users and sits on an internal hostname that partners are never given.

Which students belong to a project

A student is in a project for a school when both are true:

  1. the student is in one of the project's batches, and
  2. the student's own school (Student.schoolId) is one of the project's schools.
Why both checks. CADB batches can list more than one school. Filtering by batch alone would show a principal the names and marks of another school's children who share the batch. Students with no school set appear in no partner data at all. A data-quality report before launch lists them so they can be fixed in CADB.

Students in two programs

One child keeps one CADB record, never two admissions. Stage 1 handles SIP + ASP students through batches, so marks and attendance show correctly in both projects. Fees stay on the student record as today. Stage 2 (Enrolment) moves admission and fees per project. It changes CADB's fee screens, so it is outside this phase's no-CADB-change boundary and needs its own release plan.

Roles and overrides

  • Admins define a handful of partner roles (e.g. "Principal – standard", "Regional head", "Management"). Each role sets which reports a user can view and download, and which data groups those reports include.
  • Each partner user has one role plus their project and school grants. Per-user exceptions override the role for that person only.
  • Shortcuts for 20+ principals: "grant every school in this project", "copy access from another user", bulk invite from a spreadsheet.
  • Every grant change is logged with who changed what, and when.

Screens

partner-admin (Centum staff)

  • Partners: name, branding, domain, email sender.
  • Projects: create, edit, archive; type, dates, starting year, grades, schools, boards per grade range.
  • Batch assignment: list of CADB batches with a project picker and bulk assign; "unassigned" filter.
  • Users & access: invite, deactivate, role, project and school grants, overrides, copy-from.
  • Roles: report × view/download × data-group matrix.
  • Activity: who viewed and downloaded what, with row counts; filters by user, report, date.
  • Data quality: students without a school, batches without a project, ranges that overlap.

partner-web (principals and management)

  • Home: headline numbers for the schools the user may see, with a project switcher.
  • School view: enrolment vs target, attendance, exam performance, assignment submissions; drill down to grade, batch and student where the level allows.
  • Comparison: schools side by side (named only at Full or Summary, anonymised at Benchmark).
  • Reports: pick a report and filters, preview, download PDF or Excel.
  • Account: change password, sign out. Mobile-friendly throughout.

How files are made

  • partner-web's server fetches the data from partner-api and builds the file, so all branding and templates live outside CADB.
  • Built on request and never stored on a server.
  • Every PDF page and every Excel file's properties carry "Generated for ‹user› · ‹date and time›".
  • File metadata (Author, Creator, Producer, Company) is set explicitly to the partner brand.
  • Size cap per file and a per-minute limit per user. Every download is logged with its row count.

Rollback, by layer

LayerHow to roll back
Partner servicesRedeploy the previous tag; the previous build is kept on the server as an archive.
partner schemaEvery migration ships with a reverse script. A database backup is taken before every migration. Dropping the whole schema removes Phase 2 completely and leaves CADB as it was.
CADBNothing to roll back; it is never changed in this phase.

Keeping staging a replica

  • Same-day rule: whenever a tag goes to production, the same tag goes to staging, including migrations.
  • Staging uses its own database (cadb_staging), and its config no longer points at production (fixed 11 Oct 2026).
  • Staging has no email credentials, so nothing is ever sent to real people from it.
  • Optional: refresh staging data from the latest production backup, so testing uses realistic volumes. This is a separate decision (D2).
